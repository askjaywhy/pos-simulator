Updated 2026-11-17 (HEAD c5bf19f). Source of truth: backend/server.js, backend/emv-iso8583.js.
Simulator only: not EMV- or network-certified. Cryptograms and the unpredictable number are fixed samples.

3. AUTHORIZATION FLOW  (POST /transactions/process)
=====================================================================================

  Body: card_number, exp_date (MM/YY), cvv, amount, currency=USD, merchant_id=MERCHANT01, description

  Validation, in order (each failure = HTTP 400):
    1. required fields present          "Missing required fields" (amount 0 lands here)
    2. Luhn                             "Invalid card number (Luhn check failed)"
    3. exp_date matches NN/NN           "Invalid expiration date format (MM/YY)"
    4. month 01-12                      "Invalid expiration month (01-12)"          DEF-004
    5. amount > 0, <= 2 decimals, fits DE4 n12                                       DEF-006
    6. currency in USD EUR GBP CAD AUD MXN   "Unsupported currency ..."

  Decision, in order:
    a. exact-PAN decline rule           51 / 41 / 54 / 05
    b. card expired (UTC month, simNow) 54 Expired Card                             DEF-005
    c. otherwise                        00, auth_code = AUTH + 6 hex of the txn id

  Then setAuthorizationResult(): DE39 + EMV tag 8A (ASCII hex) set from the decision   DEF-002
  Stored and returned: 0100 (iso8583) and 0110 (iso8583_response).

=====================================================================================
4. ISO 8583 MESSAGES
=====================================================================================

  hex_message = MTI + primary bitmap (16 hex) + each field's ASCII as hex, in field order.
  Simplified: no LLVAR prefixes or binary packing (the lab SOAP service has a real ASCII packer).
  Primary bitmap only, DE2-DE64. Bit 1 (secondary bitmap) never set.                 DEF-008
  DE2 everywhere outside the message object = first 6 / last 4 (411111******1111).    DEF-003

  0100 authorization request   bitmap 7038000002C08200
    DE2 PAN (truncated)   DE3 000000      DE4 amount, minor units, n12 (Math.round)  DEF-001
    DE11 STAN (sequential per process, 000001-999999, wraps)
    DE12 hhmmss / DE13 MMDD (server local time)
    DE39 decision (kept in the 0100 for compatibility)
    DE41 TERM0001 (an8)   DE42 merchant_id (ans15, space-padded)
    DE49 from currency    DE55 EMV TLV

  0110 authorization response
    echoes DE2 3 4 11 12 13 41 42 49; DE38 = last 6 of auth_code (approvals only);
    DE39 decision; DE55 = 8A only (e.g. 8A023030)

  0200 refund     DE3 200000, DE4 refund amount, new STAN, DE37 = retrieval ref of the original
  0400 reversal   DE3 000000, DE4 original amount, new STAN, DE37 as above
    DE37 = first 12 alphanumerics of the original transaction id, uppercase.

=====================================================================================
5. EMV (DE55)
=====================================================================================

  Emitted per transaction: 9F06 AID, 9F08, 9F07, 9F26, 95, 9B, 9F37, 9F10, 9F1A, 5F2A,
  9C, 9A, 9F21, plus 8A once the decision is set.
  AIDs: Visa A0000000031010, Mastercard A0000000041010, Amex A00000002501, Discover A0000001523010.
  5F2A = 0 + DE49. 9A/9F21 = local date/time. 9F26 / 9F37 are fixed samples.
  Tests assert presence and format, never cryptogram values.

=====================================================================================
6. REFUNDS AND REVERSALS
=====================================================================================

  Refund:   APPROVED only (else 422). Amount optional (default = remaining). Total capped at the
            original in integer minor units (409 + remaining_amount). Invalid amount 400.
            Status REFUNDED or PARTIALLY_REFUNDED.                                   DEF-007
  Reversal: APPROVED only (422), not after any refund (409). Sets status REVERSED, so later
            refunds and reversals are 422.
  Both run through one in-process lock, so concurrent requests can't both pass the checks.
